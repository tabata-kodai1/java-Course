# 観点3: 実装とドキュメントの整合性

## 対象ドキュメント

| ファイル | 役割 |
|---|---|
| `docs/requirements.md` | 要件定義書全体の位置づけ・用語集 |
| `docs/features.md` | 機能要件(列・カードの管理、並べ替え、一括更新、データ保存方式) |
| `docs/screens.md` | 画面設計(ユースケース、画面要素、ワイヤーフレーム、操作フロー) |
| `docs/database.md` | ER図・テーブル定義 |
| `docs/plan.md` | 開発計画、API設計表、ディレクトリ構成 |
| `docs/tech-stack.md` | 技術選定とその理由(採用/不採用ライブラリを含む) |

## チェック手順

1. **features.md vs 実装**: 「1. スコープ」に列挙された機能(列のCRUD、カードのCRUD、並べ替え、一括更新、データ保存、起動方法)それぞれについて、対応するAPI(`backend/src/main/java/com/example/kanban/*Controller.java`)とフロントエンドUI(`frontend/src/components/`)が実在するか確認する。「2. スコープ外」に書かれている機能が実装されていないか(スコープ外機能を勝手に作っていないか)もあわせて確認する。

2. **screens.md vs 実装**: 「3. 画面要素」に列挙されたUI要素(ヘッダーのボタン、列のボタン、カードの表示項目)が、実際のコンポーネント(`AppHeader.tsx`/`Column.tsx`/`Card.tsx`)に存在するか確認する。「5. 操作フロー」に書かれた操作(クリック→モーダル表示→保存、等)が実装のイベントハンドラと一致しているか確認する。

3. **plan.md「3. API設計」vs 実際のController**: `ColumnController`/`CardController`の`@GetMapping`/`@PostMapping`/`@PatchMapping`/`@DeleteMapping`を全て洗い出し、plan.mdの表に記載されたエンドポイントと突き合わせる。表にあるのに実装がない、実装にあるのに表にない、の両方向を確認する。

4. **database.md vs JPAエンティティ**: `Column.java`/`Card.java`のフィールド・アノテーション(`@Column(nullable = ...)`等)が、database.mdのテーブル定義(カラム名・NULL許可・デフォルト値)と一致しているか確認する。

5. **tech-stack.md vs 実際の依存関係**: `backend/build.gradle`・`frontend/package.json`の実際の依存ライブラリが、tech-stack.mdに記載された選定内容(バージョン、採用/不採用の理由)と矛盾していないか確認する。特に「不採用と明記されているもの」(例: dnd-kit)が実装に紛れ込んでいないか。

## 乖離が見つかった場合の分類

- **ドキュメント優先(実装を直すべき)**: ドキュメントが定めた要件を実装が満たしていない場合(例: 列CRUDが要件にあるのに未実装)
- **実装優先(ドキュメントを直すべき)**: 実装が正しく動いていて、単にドキュメントが更新されていないだけの場合(例: 一括更新機能を実装したがdocsに追記していない)。技術選定の変更(SQLite→PostgreSQL等)でtech-stack.mdの決定が優先され、features.mdの古い記述が取り残されているケースもこれに該当する
- **要判断**: どちらが正か自明でない場合。ユーザーに判断を仰ぐ

いずれの場合も、報告時にどちらのパターンに該当するかを明記し、対応方針(実装追加/ドキュメント更新)を提案する。実際にどちらを直すかはユーザーの判断を待ってから着手する。
