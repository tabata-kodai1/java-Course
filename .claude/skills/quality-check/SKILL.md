# 品質チェック(quality-check)

このスキルは、java-Courseプロジェクト(Spring Boot backend + React frontend)に対して、4つの異なる角度から品質を横断的にチェックする。**問題を見つけて一覧で報告することが目的であり、指示がない限り自動修正は行わない。** 見つかった問題への対応方針(実装を直すか、ドキュメントを直すか、様子見か)はユーザーに判断してもらう。

## 4つのチェック観点

| # | 観点 | 参照ファイル |
|---|---|---|
| 1 | コード品質(Lint/フォーマット/ビルド) | `references/code-quality.md` |
| 2 | フレームワークのベストプラクティス遵守(Spring Boot/React) | `references/framework-conventions.md` |
| 3 | 実装とdocs/配下のドキュメントとの整合性 | `references/docs-consistency.md` |
| 4 | 未使用コード・基本的なセキュリティ観点 | `references/unused-and-security.md` |

ユーザーが「lintだけ」「ドキュメントとの整合性だけ確認して」のように観点を絞って依頼した場合は、該当する観点のみを実施する。単に「品質チェックして」「監査して」とだけ言われた場合は、4つ全てを順番に実施する。

## 実行手順

### Step 1: コード品質チェック

`references/code-quality.md`の手順に従い、backendは`./gradlew check`、frontendは`npm run lint`と`npm run build`を実行する。失敗・警告が出た箇所をすべて記録する。

### Step 2: フレームワークのベストプラクティス確認

`references/framework-conventions.md`のチェックリストを参照しながら、backendの`Controller`/`Service`/`Repository`層、frontendの主要コンポーネントを実際に`Read`し、Spring Boot・Reactの標準的な構成から外れている箇所がないか確認する。チェックリストを機械的に当てはめるのではなく、実際のコードを読んで判断すること。

### Step 3: ドキュメント整合性チェック

`references/docs-consistency.md`の手順に従い、`docs/`配下の各ドキュメント(requirements.md/features.md/screens.md/database.md/plan.md/tech-stack.md)に書かれている要件・API設計・画面要素・DBスキーマと、実際の実装(Controller/Entity/フロントエンドコンポーネント)を突き合わせる。一致していない箇所は「ドキュメントが実装より進んでいる(未実装の要件)」なのか「実装がドキュメントより進んでいる(ドキュメント未更新の機能)」なのかを区別して記録する。

### Step 4: 未使用コード・セキュリティ観点チェック

`references/unused-and-security.md`の手順に従い、`Grep`でエンドポイント・コンポーネントの参照元を確認して未使用(orphan)なものを洗い出し、あわせて入力バリデーションや例外処理まわりの基本的なセキュリティ観点を確認する。

## レポート形式

チェックが終わったら、以下の形式で指摘事項をまとめて報告する。問題がない観点は「問題なし」と明記し、省略しない。

```markdown
## 品質チェック結果

### 1. コード品質
- [結果: 合格/要修正] コマンド実行結果の要約

### 2. フレームワークのベストプラクティス
- [重大度: 要修正/推奨/参考] 指摘内容 — 該当ファイル:行 — 理由

### 3. ドキュメント整合性
- [ドキュメント優先/実装優先/要判断] 指摘内容 — 該当ドキュメント・実装箇所

### 4. 未使用コード・セキュリティ
- [重大度: 要修正/推奨/参考] 指摘内容 — 該当ファイル:行
```

重大度の目安:
- **要修正**: バグ・セキュリティ上の欠陥・ドキュメント上の要件を満たしていない未実装機能など、実害があるもの
- **推奨**: デファクトスタンダードからの逸脱だが動作には支障がないもの(例: 例外ハンドラ未実装、フォーマッタ未導入)
- **参考**: 将来的に検討してもよい程度の軽微な指摘

## 報告後の進め方

報告を提示したら、どの指摘に対応するかをユーザーに確認してから着手する。CLAUDE.mdのGit運用ルール(Issue作成 → ブランチ作成 → PR作成、GitHub操作前にユーザー確認)に従って対応すること。サーバーを起動して動作確認する場合は`start-servers`スキルのルール(デフォルトポート厳守)に従う。
