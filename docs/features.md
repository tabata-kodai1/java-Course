# 機能要件

[要件定義書](requirements.md)に戻る

## 1. スコープ（今回作る機能）

### 1.1 列（カテゴリ）の管理
- 列を自由に追加できる
- 列の名前を自由に変更できる
- 列を削除できる（列の中にカードがあっても削除できる）

初期状態では「未着手」「進行中」「完了」の3列を用意する（あくまで初期値であり、後から自由に変更・削除できる）。

### 1.2 カードの管理
- カードには以下の項目を持たせる
  - タイトル（必須）
  - 説明文（任意）
  - 期日（任意）
  - 優先度（任意、「高」「中」「低」の3段階。未指定時は「中」とする）
  - ※担当者・ラベル・添付ファイルは持たせない
- カードを列に追加できる
- カードの内容（タイトル・説明文・期日・優先度）を編集できる
- カードを削除できる

### 1.3 カードの移動・並べ替え
- ドラッグ＆ドロップで、カードを別の列に移動できる
- ドラッグ＆ドロップで、同じ列内でのカードの並び順を自由に変更できる（Trelloのような自由な並び替え）
- 各列の「優先度順」「期限順」ボタンを押すと、その列内のカードがその基準で一括で並び替えられる
  - これはボタン押下時に一度だけ並び順を並べ替える操作であり、常時そのソート順を維持し続ける「ソートモード」ではない
  - 並び替え後も、引き続きドラッグ＆ドロップで自由に並び順を変更できる

### 1.4 カードの一括更新
- カードを複数選択（チェックボックス）できる
- 選択したカードに対して、優先度・期日をまとめて変更できる（一括更新ツールバーから適用）
- 一括更新は「優先度のみ」「期日のみ」「両方」のいずれでも適用でき、指定しなかった項目は変更されない

### 1.5 データの保存
- ブラウザを閉じたり再読み込みしたりしても、入力した内容が消えずに残る
- 保存先はPostgreSQLデータベース（ローカルでは自分のパソコン上、AWS環境ではRDS。バックエンドAPIを経由して読み書きする。詳細は[tech-stack.md](tech-stack.md)を参照）

### 1.6 アプリの起動方法
- **ローカル（開発用）**：`index.html`を`file://`で直接開く方式ではなく、パソコン上でバックエンドサーバー（Java/Spring Boot）を起動し、ブラウザから`http://localhost:5173`（フロントエンド開発サーバー、APIは`http://localhost:8080`にプロキシ）でアクセスして使用する
- **AWS環境**：Terraformで構築したEC2上で、nginxが画面を配信し`/api`をバックエンドへ中継する。ブラウザからデプロイしたURLにアクセスして使用する。構築・デプロイの手順は[README](../README.md)の「AWSデプロイ」を参照
- サーバーを起動していない間はアプリを利用できない

### 1.7 カードの検索
- ヘッダーの検索欄にキーワードを入力すると、タイトルまたは説明文にキーワードを含むカードだけが各列に表示される（大文字・小文字は区別しない）
- 検索は表示を絞り込むだけで、データは変更しない

## 2. スコープ外・将来のバックログ

今回は実装しないが、将来的にやりたいこと・検討事項として記録しておく。

- 複数のボードを作って切り替えられるようにする
- カードにラベル（色分けタグ）をつけられるようにする
- カードに担当者を設定できるようにする
- カードに画像やファイルを添付できるようにする
- スマートフォンや他のパソコンからもアクセスできるようにする（アカウント・認証機能。現在のAWS環境は、許可した自分のIPからのみアクセスできる）
- 複数人での共同編集
- 期日が近い／過ぎたカードを強調表示する
- データのエクスポート／インポート（バックアップ機能）

## 3. 非機能要件

| 観点 | 要件 | 理由・補足 |
|---|---|---|
| 性能 | 列数・カード数が数十件程度であれば、操作に目立った遅延が生じないこと | 個人利用を想定しており、大量データは想定しない |
| 可用性・データ保全 | データはPostgreSQLデータベース（ローカルはDocker、AWS環境はRDS）に保存され、そのデータベースを削除しない限りブラウザやキャッシュの状態に関わらず保持されること。AWS環境では、EC2を作り直してもデータが保持されること | サーバー（データベース）側にデータを持つため、ブラウザ側の状態に依存しない。AWS環境を`terraform destroy`で削除するとデータも消える。バックアップ／エクスポート機能は今回のスコープ外とする（2章参照） |
| セキュリティ | 個人情報・機密情報の入力は想定しないこと。また、サーバーはローカルでは自分のパソコン内でのみ動作させ、AWS環境では許可した自分のIPからのみアクセスできる状態にすること（不特定多数に公開しない）。AWS環境のDBはインターネットに公開せず、アプリのサーバーからのみ接続できること | ログイン機能・認証機能を持たない個人利用前提の構成であり、不特定多数に公開すると誰でもデータを読み書きできてしまうため。構成の詳細は[tech-stack.md](tech-stack.md)の「5. インフラ構成（AWS）」を参照 |
| ユーザビリティ | 初めて開いた利用者でも、主要な操作（追加・編集・削除・移動）が画面を見ただけで直感的に行えること | 操作マニュアルは作成しない前提のため、UI自体の分かりやすさで担保する |
| 保守性・拡張性 | 将来的な機能追加（2章のバックログ）を見据え、列・カードの処理をある程度分離した構成にすること | 学習目的のため、拡張しやすいコードの書き方も習得対象とする |
| 互換性 | 主要ブラウザ（Chrome、Edge、Firefoxなど）の最新版で動作すること | 特定ブラウザへの依存を避けるため |
| 動作方式 | バックエンドサーバー（Java/Spring Boot）を起動した状態で、ローカルでは`http://localhost`経由、AWS環境ではnginx経由のURLで、ブラウザからアクセスして動作すること。`index.html`を`file://`で直接開く方式は取らない | データベースを利用するため、ブラウザから直接ファイルを読み書きする方式では実現できないため |
| 環境構築・再現性 | AWS環境は、マネジメントコンソールの手作業ではなくコード（Terraform）で構築し、コマンドだけで作成・再現・削除できること | 手作業による設定のずれを防ぎ、環境を作り直しても同じ状態に戻せるようにするため |
| コスト | AWS環境は個人利用の最小構成とし、新規アカウントの無料クレジット枠内に収めること。使わない期間は環境を削除できること | 無料枠ではなくクレジットを消費する方式のため、起動したままにすると消費し続けるため |
